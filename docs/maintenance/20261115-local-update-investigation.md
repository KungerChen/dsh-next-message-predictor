## 用户需要

本机已更新的插件文件应尽量在当前 DSH 中生效。即使新旧文件的版本号同为 0.7.0，也需能识别实际内容是否更新。若无法避免重启，希望只在确有版本不一致且有必要时提供一键重启 DSH。当前调查覆盖本机已更新的插件文件。

## 已核实的宿主边界

- DSH `0.2.2-rc.3` 提供 `hmr.runExclusive(() => hmr.reconcileProfile(...))`。协调范围是整个 profile，调用它可能处理其他插件的待协调变更。
- 普通插件配置保存沿配置处理路径执行，无法据此确认 Host 代码与浏览器 bundle 已换成磁盘上的新内容。
- 当前未找到插件可调用的通用 DSH Desktop 重启 IPC。桌面重启入口的可行性仍待调查。

## 隔离验证计划

在隔离 profile 用 fixture 更新 Host 与客户端文件，保持版本号不变，以运行时标记、bundle 指纹、页面变化及 DSH PID 验证是否生效。分别观察触发协调的插件能否更新自身，以及协调失败时旧版本能否继续工作或恢复。验证过程及证据见下文。0.7.0 已验收的功能与工作区基线见 [上一轮维护记录](20261115-focus-tab-send.md#20261115-focus-tab-send)。

## 首轮隔离观察

- DSH `0.2.2-rc.3` 上，独立 fixture 调用公开 HMR API 后，Host PID 和 0.7.0 版本号保持相同，目标 Host 的实际 ESM 标记从 A 变为 B。另一个本地链接插件也由 A 变为 B，印证整个 profile 的协调范围。返回无警告，`pending` 为空。
- 仍打开的浏览器页先执行了客户端 B，当时 Host 仍为 A。客户端与 Host 存在短暂新旧混跑，当前接口没有提供两端原子切换。
- 首轮 8 项中前 7 项通过。第 8 项抓取的 URL 沿用旧启动 revision，字节比对失败并中止。当时的报告保存在 `scratch/evidence/20261115-hmr-check/REPORT-attempt-01.json`；本次隔离 3093 端口已关闭。下一轮改为核对实际 HMR 响应体，并继续验证自更新和语法错误恢复。
